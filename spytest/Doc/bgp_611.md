# BGP Test ID 6.1.1: High Prefix Scale

**Test Plan ID:** 6.1.1
**Test Category:** BGP Scalability
**Topology:** 2-node (testbed_vs_2node.yaml)

---

## Overview

This test suite validates DUT stability and correct route handling under large BGP prefix scale (≥10k routes). It includes scalable automation subtests for control-plane and data-plane verification, resource monitoring, incremental/peak injection, withdraw/recovery, route churn, IPv6 scale, VRF scale, FIB programming limits, persistence across save/reboot, and diagnostics.

### Objectives
- Verify DUT can accept and process large BGP route advertisements (10k+ prefixes)
- Monitor control-plane resource utilization (CPU, memory) during scale injection
- Validate FIB programming for large route sets
- Test incremental scaling to identify performance tipping points
- Verify clean withdrawal and recovery without resource leaks
- Measure route churn tolerance (updates per second)
- Validate IPv6 and multi-VRF scale handling
- Ensure persistence across control-plane restarts
- Collect diagnostic artifacts for failure analysis

**Requirements:**

- 1 physical or virtual link between devices
- Minimum 4GB RAM on DUT1 (for scale testing)
- Support for BGP prefix advertisement (DUT2 acts as route generator)

## Test Cases

### 6.1.1.1 - Baseline: Verify Environment & Resource Baselines

**Objective:** Collect CPU, memory, and baseline route counts before scale test to compare during/after injection.

**Preconditions:**
- Access to DUT metrics (show processes cpu, show ip route summary, show ip bgp summary)
- No heavy background traffic or prior scale tests running
- Clean BGP state

**Test Steps:**
1. Record CPU usage (1m, 5m averages)
2. Record memory usage (free/used/available)
3. Record current RIB/FIB route counts
4. Record BGP session state and existing prefix counts
5. Save baseline metrics with timestamp t0

**Commands:**
```bash
# CPU monitoring
show processes cpu

# Memory monitoring
show system-memory

# Route counts
show ip route summary
show ip bgp summary

# Save to logs for comparison
```

**Verification:**
- Baseline metrics captured successfully and stored for later comparison
- CPU usage is stable and below 30%
- Memory usage is reasonable (< 50% on fresh system)
- No existing BGP routes from previous tests

**Expected Result:** Baseline metrics recorded; no anomalies present before test

**Timeout:** 300 seconds

**Cleanup:** No configuration changes

### 6.1.1.2 - Scale Injection: Advertise 10k IPv4 Prefixes (Control-Plane Only)

**Objective:** Inject ≥10,000 IPv4 prefixes into DUT's BGP control-plane and verify BGP RIB growth and stability.

**Preconditions:**
- Prefix generator (DUT2 or external route-server) able to advertise 10k+ prefixes
- BGP peering established and stable
- Baseline metrics captured (6.1.1.1)

**Test Steps:**
1. Configure DUT2 to advertise 10,000 unique IPv4 /24 prefixes to DUT1
2. Monitor BGP RIB growth using `show ip bgp summary` and `show ip bgp count`
3. Monitor control-plane resources (CPU, memory) continuously during injection
4. Wait for BGP convergence (no new updates for configured idle time)
5. Verify all prefixes accepted and stored in RIB

**Commands:**
```bash
# On DUT2 (route generator):
router bgp <AS>
  address-family ipv4 unicast
    # Advertise prefix ranges (e.g., 100.0.0.0/24 through 100.39.15.0/24)
    network <prefix> ...
  exit

# On DUT1 (monitor):
show ip bgp summary
show ip bgp count
show processes cpu
show system-memory
```

**Verification:**
- `show ip bgp summary` indicates ~10k routes learned and stable
- BGP session remains Established throughout injection
- CPU remains under threshold (< 70%)
- Memory used remains under threshold (< 80%)
- No BGP session flaps or control-plane crashes logged

**Expected Result:** DUT accepts and stores ≥10k routes in RIB without crashing; control-plane remains responsive

**Timeout:** 3600 seconds

**Cleanup:** Withdraw all test prefixes from prefix generator

### 6.1.1.3 - FIB Programming: Ensure Large Route Set Installed into FIB

**Objective:** Verify a large portion of injected routes are programmed into FIB and that forwarding entries exist for traffic handling.

**Preconditions:**
- Test 6.1.1.2 passed and RIB contains ~10k routes
- BGP session stable

**Test Steps:**
1. Query FIB/Routing ASIC programming stats using `show ip route`
2. Compare FIB route count against RIB route count
3. Select random sample of prefixes (100 prefixes) and verify presence in FIB
4. Verify next-hop resolution for sampled prefixes
5. Send test pings/traffic to sample of injected prefixes (if data-plane available)

**Commands:**
```bash
# FIB verification
show ip route summary
show ip route | grep "^B"

# Sample specific routes
show ip route 100.0.0.0/24
show ip route 100.10.50.0/24

# Data-plane testing (optional)
ping 100.0.0.1 -c 3
ping 100.10.50.1 -c 3
```

**Verification:**
- FIB contains high percentage (>95%) of expected routes
- FIB programming completed within acceptable time (< 10 minutes)
- Sampled routes show correct next-hop (DUT2 interface)
- Data-plane pings reach expected next-hops (if tested)

**Expected Result:** FIB programming successful for majority of routes; forwarding verified for sampled prefixes

**Timeout:** 1800 seconds

**Cleanup:** Clear sample traffic and FIB verification state

### 6.1.1.4 - Incremental Injection Ramp (Observe Resource Scaling)

**Objective:** Inject prefixes in steps to measure resource growth curve and identify tipping points.

**Preconditions:**
- Prefix generator supports staged injection
- Monitoring tools available for CPU, memory, convergence time

**Test Steps:**
1. Inject prefixes in increments: 1k → 2k → 5k → 10k → 20k (as lab allows)
2. After each increment:
   - Record CPU usage
   - Record memory usage
   - Record BGP RIB count
   - Record FIB count
   - Record convergence time
3. Pause between increments (60 seconds) to allow stabilization
4. Plot resource utilization vs. prefix count

**Commands:**
```bash
# After each increment:
show ip bgp summary
show ip bgp count
show ip route summary
show processes cpu
show system-memory

# Log timestamps for convergence measurement
```

**Verification:**
- Resource utilization scales reasonably (linear or sub-linear)
- All thresholds maintained:
  - CPU < 70%
  - Memory < 80%
- No crashes or BGP session flaps observed
- Identify any increment where instability begins

**Expected Result:** DUT shows expected resource scaling; safe operation up to supported scale documented

**Timeout:** 7200 seconds (2 hours)

**Cleanup:** Withdraw prefixes and revert any test-only config

### 6.1.1.5 - Withdrawal and Recovery: Mass Withdraw of Prefixes

**Objective:** Validate that when large set of prefixes is withdrawn, the DUT clears RIB/FIB cleanly and recovers without residual resource leaks.

**Preconditions:**
- Routes from previous tests (6.1.1.2/3/4) are installed
- Resource metrics captured before withdrawal

**Test Steps:**
1. Record pre-withdrawal resource metrics
2. Initiate full withdraw from prefix generator for all injected prefixes
3. Monitor time to remove RIB entries
4. Monitor time to remove FIB entries
5. Monitor control-plane CPU and memory trends until baseline
6. Check logs for errors during withdrawal
7. Verify resources return to baseline levels

**Commands:**
```bash
# On DUT2 (withdraw routes):
router bgp <AS>
  address-family ipv4 unicast
    no network <prefix> ...
  exit

# On DUT1 (monitor):
show ip bgp summary
show ip bgp count
show ip route summary
show processes cpu
show system-memory
show logging | grep -i bgp
```

**Verification:**
- RIB entries for test prefixes cleared within timeout
- FIB entries for test prefixes cleared within timeout
- Control-plane resources return to baseline or acceptable levels
- No memory leaks evident (memory usage returns to ~baseline ± 5%)
- No error logs indicating issues during withdrawal

**Expected Result:** Clean withdraw and recovery; no persistent high-resource utilization after stabilization period

**Timeout:** 3600 seconds

**Cleanup:** Ensure all prefixes withdrawn and system stabilized

### 6.1.1.6 - Route Churn Stress (Updates Per Second) Impact

**Objective:** Measure DUT behavior under high churn (rapid add/remove/modify) and determine sustainable update rate before instability.

**Preconditions:**
- Traffic generator able to send BGP UPDATEs at configurable rates
- Baseline established for comparison

**Test Steps:**
1. Configure generator to churn subset (5k prefixes) at set update rate:
   - Start: 100 updates/sec for 5 minutes
   - Increase: 500 updates/sec for 5 minutes
   - Increase: 1000 updates/sec for 5 minutes
2. Monitor during each phase:
   - CPU usage
   - Memory usage
   - BGP session stability
   - BGP update queue sizes
   - Control-plane log errors
3. Document maximum sustainable update rate
4. If sessions flap, capture logs and identify cause

**Commands:**
```bash
# Monitor during churn:
show ip bgp summary
show ip bgp statistics
show processes cpu
show system-memory
show logging | grep -i bgp

# Check for queue buildup
show ip bgp neighbors <peer> statistics
```

**Verification:**
- DUT handles churn up to certain rate without session drops
- No control-plane OOM or crashes
- Document maximum sustainable update rate
- If sessions flap, logs captured for analysis

**Expected Result:** DUT tolerates moderate churn; beyond threshold, performance degrades — thresholds documented

**Timeout:** 7200 seconds (2 hours)

**Cleanup:** Stop churn; restore to baseline

### 6.1.1.7 - IPv6 Scale: Inject ≥10k IPv6 Prefixes

**Objective:** Repeat scale tests for IPv6 NLRI and observe control/data-plane behavior for large IPv6 route sets.

**Preconditions:**

- DUT has IPv6 BGP peering configured

**Test Steps:**

**Verification:**
- IPv6 RIB grows to expected size (~10k prefixes)

- CPU < 70%, Memory < 80%

**Expected Result:** IPv6 scale similar to IPv4 within hardware/software capabilities

**Timeout:** 3600 seconds

### 6.1.1.9 - Persistence & Reboot: Routes Survive Control-Plane Restart

**Objective:** Verify behavior across configuration save and control-plane or system reboot.

**Preconditions:**
- Routes loaded (from 6.1.1.2/3) and config saved
- System stable with known route count

**Test Steps:**
1. Verify route count before restart
2. Save configuration: `sudo config save -y`
3. Perform control-plane restart or full reboot:
   - Control-plane: `sudo systemctl restart bgp`
   - Full reboot: `sudo reboot`
4. Wait for system to come back up
5. Measure time to restore BGP sessions
6. Measure time to re-learn routes and program FIB
7. Compare resource usage to baseline

**Commands:**
```bash
# Before restart:
show ip bgp summary
show ip route summary
sudo config save -y

# Restart control-plane or reboot:
sudo systemctl restart bgp
# OR
sudo reboot

# After restart:
show ip bgp summary
show ip bgp count
show ip route summary
show processes cpu
show system-memory
```

**Verification:**
- Routes re-established within acceptable reconvergence window
- No crashes during or after restart
- CPU and memory stable post-reboot
- All BGP sessions return to Established state
- Route count matches pre-restart count (within acceptable margin)

**Expected Result:** System restores BGP sessions and route programming as per platform guarantees; reconvergence time documented

**Timeout:** 3600 seconds

**Cleanup:** Restore to baseline and withdraw prefixes

### 6.1.1.10 - Diagnostics, Logging and Failure Analysis

**Objective:** Collect diagnostic artifacts during scale test for root-cause analysis.

**Preconditions:**
- Storage available for captures and log dumps
- Monitoring configured (syslog, telemetry)

**Test Steps:**
1. Start continuous logging during injection and churn tests
2. Configure periodic telemetry snapshots (CPU, memory, BGP stats)
3. Capture BGP traffic on relevant interfaces using tcpdump:
   - During steady state
   - During failures or anomalies
4. Collect system logs from /var/log/syslog, /var/log/frr/
5. Collect BGP process logs
6. If crashes occur, collect core dumps and memory dumps
7. Archive all artifacts with timestamps

**Commands:**
```bash
# Capture BGP traffic:
sudo tcpdump -i Ethernet4 -w /tmp/bgp_scale_traffic.pcap 'tcp port 179'

# Collect logs:
sudo tar czf /tmp/scale_test_logs_$(date +%Y%m%d_%H%M%S).tar.gz \
  /var/log/syslog \
  /var/log/frr/*.log

# System state snapshot:
show tech-support > /tmp/tech_support_$(date +%Y%m%d_%H%M%S).txt

# Core dumps (if crash):
ls -lh /var/core/
```

**Verification:**
- Diagnostic artifacts captured and archived
- Timestamps correlate with test events
- Sufficient data for root-cause analysis of any failures
- Artifacts include: pcaps, logs, telemetry data, core dumps

**Expected Result:** Sufficient artifacts exist to trace failures, memory growth, control-plane stalls, or other anomalies

**Timeout:** 600 seconds

**Cleanup:** Stop captures and archive logs to central location

## Configuration Examples

### DUT1 (Route Receiver) - Basic BGP Configuration
```bash
# Interface configuration
interface Ethernet4
  no shutdown
  ip address 10.0.24.0/31
  exit

# BGP configuration
router bgp 65001
  bgp router-id 1.1.1.1
  neighbor 10.0.24.1 remote-as 65002
  address-family ipv4 unicast
    neighbor 10.0.24.1 activate
    maximum-paths 64
  exit
  exit
```

### DUT2 (Route Generator) - Prefix Advertisement
```bash
# Interface configuration
interface Ethernet4
  no shutdown
  ip address 10.0.24.1/31
  exit

# BGP configuration with prefix generation
router bgp 65002
  bgp router-id 2.2.2.2
  neighbor 10.0.24.0 remote-as 65001
  address-family ipv4 unicast
    neighbor 10.0.24.0 activate
    # Generate 10k prefixes (scripted or via route-map)
    # Example: advertise 100.0.0.0/24 through 100.39.15.0/24
    network 100.0.0.0/24
    network 100.0.1.0/24
    ...
    # (Use route generation script for actual 10k prefixes)
  exit
  exit
```

## Notes and Considerations

1. **Route Generation:** The 2-node testbed uses DUT2 as a route generator. For full-scale testing (20k+ routes), consider using external route injection tools or BGP route reflectors.

2. **Testbed Limitations:** Virtual testbeds may have lower scale limits than hardware. Adjust prefix counts accordingly:
   - Virtual: 1k-5k prefixes (for basic validation)
   - Hardware: 10k-100k prefixes (for production scale)

3. **Cleanup Important:** Always withdraw test prefixes and restore configuration to avoid persistent load on DUT.

4. **Structured Output:** Use JSON output where available (`show ip bgp summary -j`) for deterministic parsing in automation.

5. **Long-Running Tests:** Tests 6.1.1.4, 6.1.1.6, 6.1.1.8 are long-running. Schedule in isolated lab environments with monitoring.

6. **Platform-Specific:** Some platforms may have different scale capabilities. Document actual observed limits for your hardware.
