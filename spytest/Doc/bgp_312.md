# BGP Test ID 3.1.2: MED Path Selection

## Test Plan Information

**Test ID:** 3.1.2
**Test Title:** MED path selection
**Topology:** `./testbeds/testbed_vs_2node.yaml`

## Objective

Verify that BGP prefers the path with the lower MED (Multi-Exit Discriminator) when earlier best-path attributes tie.

## Description

These subtests validate MED behavior in IPv4 and IPv6 across eBGP and iBGP scenarios, interactions with LOCAL_PREF (which should win), MED propagation, tie-breaker behavior, and effect of route-maps/policies.

MED (Multi-Exit Discriminator) is a BGP path attribute used to influence inbound routing decisions. When multiple paths to the same destination exist and earlier attributes (LOCAL_PREF, AS-PATH length, ORIGIN) are equal, the path with the lower MED value is preferred.

## Topology Requirements

- **Minimum Devices:** 2 DUTs (D1, D2)
- **Links:** 1 direct link between D1 and D2
- **Testbed File:** `./testbeds/testbed_vs_2node.yaml`

## BGP Best Path Selection Order

For reference, BGP best path selection follows this order:
1. Weight (Cisco proprietary, highest preferred)
2. **LOCAL_PREF (highest preferred)**
3. Local route (originated by this router)
4. **AS-PATH length (shortest preferred)**
5. **ORIGIN (IGP < EGP < Incomplete)**
6. **MED (lowest preferred)** ← Focus of this test
7. eBGP over iBGP
8. IGP metric to next-hop
9. Oldest route (for eBGP)
10. Router ID (lowest)
11. Neighbor IP address (lowest)

MED is only compared by default when routes come from the same neighboring AS. The `bgp always-compare-med` configuration changes this behavior.

## Test Cases

### Test 3.1.2.1: Basic MED preference (two eBGP peers, IPv4)

**Objective:**
Two eBGP peers advertise the same IPv4 prefix with different MEDs; verify the path with lower MED is selected when LOCAL_PREF, AS-PATH, ORIGIN tie.

**Preconditions:**
- D1 and D2 configured as eBGP peers to two separate external advertisers (or test injectors) that can advertise the same prefix
- BGP sessions Established and both peers advertise the test prefix

**Test Steps:**
1. Configure peer A to advertise 198.51.110.0/24 with MED=200
2. Configure peer B to advertise 198.51.110.0/24 with MED=100
3. Ensure LOCAL_PREF and AS-PATH lengths are equal between the two paths, and ORIGIN is same
4. On internal observing router, run `show ip bgp 198.51.110.0/24`

**Configuration Example (Klish):**

On D1 (AS 65001) receiving routes from external peers:
```bash
# Configure BGP neighbors and policies to set different MEDs
router bgp 65001
  neighbor 10.0.0.2 remote-as 65100
  neighbor 10.0.0.6 remote-as 65200

  address-family ipv4 unicast
    neighbor 10.0.0.2 activate
    neighbor 10.0.0.6 activate
    neighbor 10.0.0.2 route-map SET_MED_200 in
    neighbor 10.0.0.6 route-map SET_MED_100 in
  exit-address-family
exit

route-map SET_MED_200 permit 10
  set metric 200
exit

route-map SET_MED_100 permit 10
  set metric 100
exit
```

On D2 (AS 65100) advertising the prefix:
```bash
router bgp 65100
  neighbor 10.0.0.1 remote-as 65001

  address-family ipv4 unicast
    network 198.51.110.0/24
  exit-address-family
exit
```

**Verification (Click):**
```bash
# Show BGP routes with MED values
show ip bgp 198.51.110.0/24

# JSON output for automation
show ip bgp 198.51.110.0/24 json
```

**Expected Output:**
```json
{
  "paths": [
    {
      "prefix": "198.51.110.0/24",
      "med": 100,
      "bestpath": true,
      "nexthops": [{"ip": "10.0.0.6"}]
    },
    {
      "prefix": "198.51.110.0/24",
      "med": 200,
      "bestpath": false,
      "nexthops": [{"ip": "10.0.0.2"}]
    }
  ]
}
```

**Verification Points:**
- `show ip bgp 198.51.110.0/24 json`: Check `bestpath` and `med` fields; best path should have med=100
- Confirm forwarding follows selected path (simple ping/traceroute or traffic generator)

**Expected Result:**
Path with lower MED (100) is selected as the best path when earlier attributes tie.

**Timeout:** 60 seconds

**Cleanup:**
- Withdraw advertisements and remove test MED settings

### Test 3.1.2.2: MED tie with AS-PATH difference (AS-PATH shorter wins over MED)

**Objective:**
Validate that when LOCAL_PREF equal, AS-PATH is considered before MED (i.e., shorter AS-PATH wins even if its MED is higher).

**Preconditions:**
- Two eBGP-learned paths to same prefix where one has a shorter AS-PATH but higher MED

**Test Steps:**
1. Peer A advertises prefix with AS-PATH length 2 and MED=500
2. Peer B advertises same prefix with AS-PATH length 4 and MED=100
3. On observer, inspect `show ip bgp <prefix>`

**Configuration Example (Klish):**

On D2 (Peer A - AS 65100):
```bash
# Advertise with AS-PATH length 2 (65100 65300) and MED=500
router bgp 65100
  neighbor 10.0.0.1 remote-as 65001

  address-family ipv4 unicast
    network 198.51.120.0/24
    neighbor 10.0.0.1 route-map ASPATH_SHORT_MED_HIGH out
  exit-address-family
exit

route-map ASPATH_SHORT_MED_HIGH permit 10
  set as-path prepend 65300
  set metric 500
exit
```

On D2 (Peer B - AS 65200) or simulated:
```bash
# Advertise with AS-PATH length 4 and MED=100
route-map ASPATH_LONG_MED_LOW permit 10
  set as-path prepend 65400 65500 65600
  set metric 100
exit
```

**Verification (Click):**
```bash
show ip bgp 198.51.120.0/24
show ip bgp 198.51.120.0/24 json
```

**Verification Points:**
- Verify best-path chosen is the one with shorter AS-PATH (peer A) despite its higher MED
- AS-PATH length should be visible in output

**Expected Result:**
AS-PATH (shorter) is chosen before MED comparison — MED only used after AS-PATH tie.

**Timeout:** 60 seconds

**Cleanup:**
- Remove test advertisements and AS-PATH prepends

### Test 3.1.2.4: MED propagation across eBGP/iBGP (next-hop/MED behavior)

**Objective:**
Verify how MED is propagated: MED is advertised by one AS to another but not necessarily forwarded by iBGP unchanged unless policies allow it.

**Preconditions:**
- Topology where route is learned via eBGP at D1, then advertised into same AS (iBGP) to D2 and out to another eBGP peer

**Test Steps:**
1. Peer external X to D1 advertises prefix with MED=50
2. D1 advertises into iBGP to D2 without changing MED by default
3. D2 advertises to its external peer; check what MED is sent out (depends on config/policy)

**Configuration Example (Klish):**

On D1 (eBGP to external, iBGP to D2):
```bash
router bgp 65001
  neighbor 10.0.0.10 remote-as 65300  # External peer
  neighbor 10.1.0.2 remote-as 65001   # iBGP to D2

  address-family ipv4 unicast
    neighbor 10.0.0.10 activate
    neighbor 10.1.0.2 activate
  exit-address-family
exit
```

**Verification (Click):**
```bash
# On D1
show ip bgp 198.51.140.0/24
show ip bgp neighbors 10.1.0.2 advertised-routes

# On D2
show ip bgp 198.51.140.0/24
show ip bgp neighbors <external-peer> advertised-routes
```

**Verification Points:**
- Use `show ip bgp <prefix>` on each hop to inspect MED values
- Use `show ip bgp neighbors <peer> advertised-routes` to check MED in advertisements

**Expected Result:**
MED is attached by advertising AS and is carried across to eBGP neighbors of the next AS unless policy modifies it; iBGP typically propagates MED unchanged but MED comparison behavior limited to neighboring ASs.

**Timeout:** 120 seconds

**Cleanup:**
- Withdraw test adverts and revert policy

### Test 3.1.2.5: MED comparison only for routes from same neighboring AS (MED scope)

**Objective:**
Confirm MED is only comparable when paths are from the same neighboring AS (unless `bgp always-compare-med` configured).

**Preconditions:**
- Two different neighboring ASes advertise same prefix with different MEDs

**Test Steps:**
1. Peer A (AS 65100) advertises prefix with MED=20 to D1
2. Peer B (AS 65200) advertises same prefix with MED=10 to D1
3. On D1, inspect `show ip bgp <prefix>` for chosen best-path

**Configuration Example (Klish):**

On D1:
```bash
router bgp 65001
  neighbor 10.0.0.2 remote-as 65100  # Peer A
  neighbor 10.0.0.6 remote-as 65200  # Peer B

  address-family ipv4 unicast
    neighbor 10.0.0.2 activate
    neighbor 10.0.0.6 activate
  exit-address-family
exit

# To test with always-compare-med (optional):
# router bgp 65001
#   bgp always-compare-med
# exit
```

**Verification (Click):**
```bash
show ip bgp 198.51.150.0/24
show ip bgp 198.51.150.0/24 json
show ip bgp summary
```

**Verification Points:**
- If default behavior, MEDs are not compared across different neighboring ASes; selection follows AS-PATH/LOCAL_PREF rules
- If `bgp always-compare-med` enabled, MED would be compared globally

**Expected Result:**
By default MED is compared only for paths from same neighbor AS — path selection should not choose B solely due to lower MED in a different AS unless `always-compare-med` is set.

**Timeout:** 60 seconds

**Cleanup:**
- Withdraw test advertisements

### Test 3.1.2.10: Persistence and convergence - MED changes and convergence time measurement

**Objective:**
Change MED dynamically and measure time for best-path switch and route convergence across peers.

**Preconditions:**
- Baseline routes present; initial best-path known

**Test Steps:**
1. Change MED on path A from 100 to 1000 via policy update at time t0
2. Poll `show ip bgp <prefix>` on observing router until new best-path selected; record t1
3. Compute convergence time = t1 - t0

**Configuration Example (Klish):**

Initial state:
```bash
route-map MED_PATH_A permit 10
  set metric 100
exit
```

Changed state (at time t0):
```bash
route-map MED_PATH_A permit 10
  set metric 1000
exit

# Apply to neighbor
router bgp 65001
  address-family ipv4 unicast
    neighbor 10.0.0.2 soft-reconfiguration inbound
  exit-address-family
exit

# Trigger route refresh
clear ip bgp 10.0.0.2 soft in
```

**Verification (Click):**
```bash
# Repeated polling (automation)
while true; do
  show ip bgp 198.51.180.0/24 json
  sleep 1
done
```

**Verification Points:**
- Best-path shifts to alternative path within acceptable window
- Document convergence time for regression tracking
- Convergence time should be < 10 seconds typically

**Expected Result:**
MED-driven change results in timely best-path update; convergence time recorded and within SLA.

**Timeout:** 300 seconds

**Cleanup:**
- Restore original MED values and policies
