# BGP Test ID 3.1.5: ECMP Path Installation

## Overview
This test suite validates BGP Equal-Cost Multi-Path (ECMP) behavior in SONiC, ensuring that when multiple BGP peers advertise the same prefix with identical attributes, the device installs multiple equal-cost paths for load balancing.

```
# Topology - 2 nodes (for basic tests; some subtests require lab setup)
# +------------------------+                       +------------------------+
# |    D1 (smic_sonic1)    |                       |    D2 (smic_sonic2)    |
# |  AS 65001              |                       |  AS 65002              |
# |  Lo0: 1.1.1.1/32       |                       |  Lo0: 2.2.2.2/32       |

```

**Note**: Some test cases (particularly scale and multi-peer tests) require more than 2 physical devices or use of route generators. These are marked as lab/manual tests.

## Test Cases

### Test 3.1.5.1: Basic IPv4 ECMP - Control Plane & RIB Verification

**Objective**: Enable BGP multipath and verify two equal-cost IPv4 paths for the same prefix are present in the BGP RIB with advertised next-hops visible.

**Preconditions**:
- Two peers advertise identical IPv4 prefix with same attributes (LOCAL_PREF, AS-PATH length, ORIGIN, MED)
- BGP sessions Established with both peers
- Multipath enabled on observing DUT

**Test Steps**:
1. Configure loopback interfaces on D2 (Lo10, Lo11) to simulate multiple peers
2. Ensure both peers advertise same prefix (e.g., 198.51.120.0/24) with identical attributes
3. On D1 (observer), enable multipath: `maximum-paths <N>` in BGP configuration
4. Wait for routes to converge (typically 30-60 seconds)
5. Verify BGP RIB shows multiple paths

**Verification**:
- `show ip bgp 198.51.120.0/24 json` lists multiple paths with `"paths"` length >= 2
- `show ip route 198.51.120.0/24` shows multiple next-hops or ECMP entry
- BGP RIB indicates multipath/ECMP usage

**Expected Result**: BGP RIB contains multiple equal-cost paths; next-hops list >= 2

**Timeout**: 90 seconds

**CLI Type**: klish for config, click for verification

### Test 3.1.5.2: IPv4 ECMP - FIB Programming & Data-Plane Verification

**Objective**: Verify equal-cost BGP paths are installed into FIB/forwarding plane and traffic is forwarded via multiple next-hops.

**Preconditions**:
- Subtest 3.1.5.1 passed (RIB shows multipath)
- Traffic generator or test hosts available

**Test Steps**:
1. Configure traffic flows to target prefix (vary source port/IP for ~200 flows)
2. Collect per-egress interface counters on DUT
3. Monitor traffic distribution across next-hops
4. Optionally capture packets to verify distribution

**Verification**:
- Per-next-hop or per-interface counters show traffic distributed (not all on single path)
- Ping/traceroute shows correct path resolution
- Verify connectivity through each next-hop

**Expected Result**: Traffic distributed across ECMP next-hops

**Timeout**: 180 seconds

**CLI Type**: klish for config, click for verification

---

### Test 3.1.5.3: Max-Paths Limit - Honor Configured ECMP Limit

**Objective**: Verify device honors configured max-paths limit and installs only up to that many next-hops.

**Preconditions**:
- At least N peers (>= max-paths) advertising same prefix with identical attributes
- Lab environment with route generators or multiple peers

**Test Steps**:
1. Configure max-paths to chosen value (e.g., 2 or 4) via `maximum-paths N`
2. Ensure at least that many equal-cost paths available from peers
3. Inspect RIB/FIB for number of installed nexthops
4. Verify installed paths don't exceed configured limit

**Verification**:
- `show ip bgp <prefix>` shows paths >= available peers
- FIB/RIB installation limited to configured max-paths
- `show ip route <prefix>` indicates ECMP entries count = configured max

**Expected Result**: Only up to configured max-paths next-hops installed into FIB; extra paths remain in RIB only

**Timeout**: 120 seconds

**CLI Type**: klish for config, click for verification

---

### Test 3.1.5.4: ECMP IPv6 - Multipath for IPv6 Prefixes

**Objective**: Verify BGP multipath behavior for IPv6 routes (multiple next-hops installed and data-plane distribution).

**Preconditions**:
- IPv6 peering and multipath capability enabled
- Peers advertise identical IPv6 prefix with identical attributes

**Test Steps**:
1. Enable IPv6 multipath if platform requires separate knob
2. Advertise test IPv6 prefix (e.g., 2001:db8:120::/64) from multiple peers
3. Inspect `show ipv6 bgp <prefix>` and `show ipv6 route <prefix>`
4. Verify multiple next-hops present

**Verification**:
- Multiple next-hops visible in BGP RIB and FIB for IPv6 prefix
- Traffic to prefix distributed across nexthops
- IPv6 forwarding functional through all paths

**Expected Result**: IPv6 ECMP works similarly to IPv4; multiple next-hops installed and traffic distributed

**Timeout**: 180 seconds

**CLI Type**: klish for config, click for verification

### Test 3.1.5.5: Unequal Attributes Not Eligible for ECMP (Negative Case)

**Objective**: Verify that when attributes differ (LOCAL_PREF, AS-PATH, MED, weight), ECMP is not installed—only single best path selected.

**Preconditions**:
- Two paths exist but have differing attributes

**Test Steps**:
1. Configure path A with LOCAL_PREF 200, path B with LOCAL_PREF 100 (or different AS-PATH length)
2. Inspect `show ip bgp <prefix>` and `show ip route <prefix>`
3. Verify only one path is selected as best

**Verification**:
- Only single best-path is chosen (no ECMP installed)
- FIB reflects only that next-hop
- Higher LOCAL_PREF or shorter AS-PATH wins

**Expected Result**: ECMP not used when BGP path attributes are not equal per selection rules

**Timeout**: 60 seconds

**CLI Type**: klish for config, click for verification

---

### Test 3.1.5.6: ECMP Hashing and Flow Consistency

**Objective**: Verify hashing behavior: flows with identical 5-tuple land on same ECMP nexthop (flow-consistency); different flows distributed.

**Preconditions**:
- ECMP installed with multiple nexthops (subtest 3.1.5.1/2 passed)
- Traffic generator capable of generating multiple distinct flows

**Test Steps**:
1. Generate multiple flows with same 5-tuple repeatedly
2. Verify they consistently go to same nexthop
3. Generate flows with varying 5-tuple fields
4. Verify distribution across nexthops
5. Measure packet reorder/latency

**Verification**:
- Flows with same 5-tuple map consistently to same nexthop
- Varied flows distributed across available nexthops
- No excessive packet reordering for consistent flows

**Expected Result**: ECMP uses hashing algorithm providing per-flow consistency; distribution observed for varied flows

**Timeout**: 180 seconds

**CLI Type**: klish for config, click for verification

---

### Test 3.1.5.7: ECMP Reaction to Next-Hop Withdraw (Dynamic Removal)

**Objective**: Verify when one ECMP next-hop becomes unreachable/withdrawn, FIB updates to remove that nexthop and traffic shifts without blackholing.

**Preconditions**:
- ECMP with >=2 nexthops installed
- Traffic baseline running

**Test Steps**:
1. Withdraw or shut down one of the next-hops (simulate failure)
2. Monitor `show ip route <prefix>` and FIB programming
3. Observe data-plane: traffic should redistribute to remaining nexthops
4. Restore next-hop and verify re-addition to ECMP set

**Verification**:
- FIB updates to remove failed nexthop
- No persistent forwarding blackhole
- Traffic redistributed to remaining paths
- When restored, nexthop reappears in ECMP set

**Expected Result**: Dynamic ECMP reprogramming works; failover smooth with minimal packet loss for new flows

**Timeout**: 180 seconds

**CLI Type**: klish for config, click for verification

---

### Test 3.1.5.8: Persistence - ECMP Configuration After Config Save & Reboot

**Objective**: Ensure multipath configuration and installed ECMP next-hops persist across config save and device reboot.

**Preconditions**:
- ECMP active with installed nexthops
- Traffic verification achieved

**Test Steps**:
1. Save configuration (`write memory` or `config save`)
2. Perform warm or cold reboot
3. After reboot, verify `show ip bgp <prefix>` and `show ip route <prefix>`
4. Verify ECMP nexthops and FIB programmed
5. Verify data-plane (ping/traffic)

**Verification**:
- ECMP config and next-hops persist
- Forwarding restored after reboot
- Reconvergence time measured and acceptable
- All paths operational

**Expected Result**: ECMP restored and functional after reboot; routes reinstalled into FIB

**Timeout**: 600 seconds

**CLI Type**: klish for config, click for verification

---

### Test 3.1.5.9: Scale & Performance - Many ECMP Nexthops (Lab/Manual)

**Objective**: Measure device behavior when large number of ECMP nexthops programmed (lab-only or manual).

**Preconditions**:
- Lab environment with route-generators (NOT typical 2-node testbed)
- Capability to simulate many peers

**Test Steps**:
1. Program many equal-cost next-hops (N) for prefix via test harness
2. Monitor CPU, memory, ASIC programming time
3. Monitor route programming latencies
4. Verify forwarding behavior under scale

**Verification**:
- Device programs up to supported ECMP limits without crashing
- Performance metrics within acceptable thresholds
- CPU/memory usage acceptable
- No forwarding failures

**Expected Result**: Device supports documented ECMP scale; above-scale conditions handled gracefully (errors logged, excess paths kept in RIB only)

**Timeout**: 1200 seconds

**CLI Type**: klish for config, click for verification

**Notes**: Scale tests are lab-only and may be skipped in CI

---

### Test 3.1.5.10: Negative - ECMP Disabled Ensures Single Best Path

**Objective**: Verify when multipath is disabled, only single best path installed even if multiple equal-cost paths exist.

**Preconditions**:
- Multiple equal-cost paths exist
- Device multipath feature disabled or set to 1

**Test Steps**:
1. Disable multipath or set max-paths=1
2. Inspect `show ip bgp <prefix>` and `show ip route <prefix>`
3. Verify only single path installed

**Verification**:
- Only one next-hop installed in FIB
- No ECMP distribution
- Single best path selected per BGP selection algorithm

**Expected Result**: No ECMP when multipath disabled; single best path installed

**Timeout**: 60 seconds

**CLI Type**: klish for config, click for verification

## Configuration Examples

### Enable BGP Multipath (klish)
```
configure terminal
router bgp 65001
 address-family ipv4 unicast
  maximum-paths 4
 exit-address-family
exit
```

### Enable BGP Multipath for IPv6 (klish)
```
configure terminal
router bgp 65001
 address-family ipv6 unicast
  maximum-paths 4
 exit-address-family
exit
```

### Configure Static Route to Loopback (for multi-peer simulation)
```
configure terminal
interface Loopback10
 ip address 10.2.10.1/32
exit
interface Loopback11
 ip address 10.2.11.1/32
exit
```

### Advertise Prefix from Multiple Sources
```
configure terminal
router bgp 65002
 address-family ipv4 unicast
  network 198.51.120.0/24
 exit-address-family
exit
```

## Notes

- **Topology Limitation**: The 2-node testbed can simulate ECMP scenarios using multiple loopback interfaces to create multiple advertisement sources. True multi-peer scenarios require additional devices or route generators.

- **CLI Type**: Configuration uses `klish` CLI mode, verification uses `click` commands for structured JSON output.

- **Multipath Configuration**: The `maximum-paths` setting controls how many equal-cost paths BGP will install. Default is typically 1 (no ECMP).

- **Traffic Testing**: Data-plane verification requires traffic generation tools (IXIA, TRex, scapy) or simple ping/traceroute tests.

- **Scale Tests**: Test 3.1.5.9 requires lab environment and is marked as manual/optional for CI pipelines.

- **Platform Differences**: ECMP capabilities may vary by platform/ASIC. Tests should adapt to platform-reported limits.

- **Hashing Algorithm**: Flow consistency (5-tuple hashing) is platform-dependent. Tests verify behavior but don't mandate specific algorithm.

- **IPv6 Support**: Requires separate address-family configuration; some platforms may have different limits for IPv4 vs IPv6 ECMP.
