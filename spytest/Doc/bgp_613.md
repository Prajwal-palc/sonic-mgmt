# BGP Test ID 6.1.3: Prefix Installation Latency Under Churn

## Test Suite Information

**Test Suite:** Prefix installation latency under churn
**Parent Test ID:** 6.1.3
**Topology:** ./testbeds/testbed_vs_2node.yaml
**Feature:** BGP Convergence and Performance

## Description

Verify prefix installation time meets SLA while prefixes are added/withdrawn (churn).
These subtests exercise increasing churn levels and a long-duration stability test to
measure BGP routing table update performance under realistic production scenarios.

## Topology Diagram

```
# Topology - 2 nodes (Route Generator + DUT)
# +--------------------+                       +--------------------+
# |  Route Generator   |                       |        DUT         |
# |    (Traffic Gen)   |=======================|   SONiC Device     |
# |                    |     BGP Session       |                    |
# +--------------------+                       +--------------------+
```

## Prerequisites

- SONiC DUT with BGP enabled
- Route generator/traffic generator reachable and controllable from test host
- NTP synchronization between DUT and test host for accurate latency measurements
- DUT has no conflicting static routes for test prefixes
- Monitoring infrastructure (prometheus/grafana) for long-duration tests
- Control-plane instrumentation enabled (FIB notifications, route-monitor socket)

## Test Cases

### Test Case 6.1.3.1: Baseline Prefix Installation (No Churn)

**Title:** baseline_prefix_installation_no_churn

**Purpose:** Establish baseline prefix installation latency with no churn.

**Objective:** Measure single-prefix and bulk-prefix installation latency when routes
are advertised once (no withdraws).

**Preconditions:**
- Topology up and stable using ./testbeds/testbed_vs_2node.yaml
- Route generator reachable and controllable from test host
- DUT has no conflicting static routes for test prefixes

**Input Parameters:**
- prefix_count: 100
- add_rate_pps: 100 (prefixes/s, burst or steady)
- withdraw_rate_pps: 0
- measurement_window_s: 60
- sla_ms_per_prefix: 50

**Test Steps:**
1. Ensure DUT control-plane and dataplane are healthy and monitoring enabled
2. Reset route generator state; configure generator to advertise prefix_count prefixes at add_rate_pps
3. Start synchronized time source (NTP) on DUT and test host
4. Start packet-capture or dataplane logs if required
5. Trigger route advertisement (add all prefixes)
6. For each prefix measure time from route advertisement timestamp to prefix installation in DUT forwarding table (RIB/NH/FIB)
7. Stop measurement after measurement_window_s or when all prefixes installed

**Measurement Method:**
- Record per-prefix: t_advertise, t_rib_update, t_fib_program
- Calculate: latency_install_ms = t_fib_program - t_advertise
- Use DUT control-plane APIs (show ip route summary / netlink or platform FIB notification)
- Correlate route-generator event timestamps with DUT events using synchronized clocks

**Expected Result:**
All prefixes installed within sla_ms_per_prefix (<=50 ms) for >= 99% of prefixes.

**Pass Criteria:**
- 99th_percentile_latency_ms <= sla_ms_per_prefix
- max_latency_ms <= 2 * sla_ms_per_prefix (warn if exceeded)
- percent_failed_installs == 0

**Artifacts to Collect:**
- Route-generator logs (advertisements, timestamps)
- DUT control-plane logs (/var/log/syslog, bgp/zebra logs)
- FIB update logs
- Packet capture at ingress/egress if needed
- Measurement CSV with per-prefix timestamps and latencies

**Automation:**
- Script: tests/convergence/test_prefix_install_baseline.py
- Timeout: 10 minutes
- Tags: [baseline, no-churn, perf]

### Test Case 6.1.3.2: Low Churn Prefix Installation

**Title:** low_churn_prefix_installation

**Purpose:** Measure installation latency when prefixes are being added and withdrawn at low churn rate.

**Objective:** Verify SLA under light churn conditions.

**Preconditions:**
- Same as 6.1.3.1

**Input Parameters:**
- prefix_count: 1000
- add_rate_pps: 200
- withdraw_rate_pps: 50
- churn_pattern: cyclic (add N, withdraw M, repeat)
- measurement_window_s: 120
- sla_ms_per_prefix: 100

**Test Steps:**
1. Configure route generator to run a cyclic pattern: add 200 prefixes/s until prefix_count reached, then withdraw at 50 prefixes/s, repeat for measurement_window_s
2. Begin synchronized logging and start DUT instrumentation (FIB notifications)
3. For each advertisement measure installation latency as in baseline
4. For each withdraw measure removal latency (time from withdraw event to FIB removal)
5. Continue for measurement_window_s

**Measurement Method:**
- Same per-prefix logging as baseline
- Additionally measure withdraw-to-FIB-removal time
- Compute 50th/90th/99th percentiles separately for add and withdraw events

**Expected Result:**
- Add_installation: 99th_percentile_latency_ms <= sla_ms_per_prefix (<=100 ms)
- Withdraw_removal: 99th_percentile_latency_ms <= 2 * sla_ms_per_prefix
- No control-plane crashes or route flaps beyond expected pattern

**Pass Criteria:**
- Add 99th <= sla, Withdraw 99th <= 2*sla
- CPU utilization on DUT control-plane < 85% during test
- Memory stable (no leaks > 5% increase over test)

**Artifacts to Collect:**
- Same as baseline
- DUT resource stats (top, vmstat)
- Route-generator summary

**Automation:**
- Script: tests/convergence/test_prefix_install_low_churn.py
- Timeout: 30 minutes
- Tags: [low-churn, perf]

### Test Case 6.1.3.3: Medium Churn Prefix Installation

**Title:** medium_churn_prefix_installation

**Purpose:** Measure behavior under moderate churn expected in production spikes.

**Objective:** Verify SLA and stability for moderate add/withdraw rates.

**Preconditions:**
- Same as above

**Input Parameters:**
- prefix_count: 5000
- add_rate_pps: 1000
- withdraw_rate_pps: 500
- churn_pattern: randomized_bursts (Poisson-like bursts)
- measurement_window_s: 300
- sla_ms_per_prefix: 200

**Test Steps:**
1. Configure generator for randomized bursts: bursts of high adds (1-2s) followed by pauses, and intermittent withdraw bursts
2. Start DUT telemetry (CPU, mem, queue depths) and FIB/RIB monitoring
3. Start the churn pattern and measure per-prefix installation/removal latencies
4. Monitor for packet loss or forwarding anomalies if test traffic is used
5. After test window, let system settle and measure time to quiesce

**Measurement Method:**
- Per-prefix installation and removal timestamps
- Aggregate percentiles and mean
- Capture DUT control-plane thread latencies and FIB programming queue lengths if available

**Expected Result:**
- 95th_percentile_latency_ms <= sla_ms_per_prefix (<=200 ms)
- System returns to baseline within 2 * (peak_burst_duration) after bursts stop
- No process restarts or core dumps

**Pass Criteria:**
- 95th <= sla
- No crashes
- Acceptable resource usage (CPU < 95% short bursts)

**Artifacts to Collect:**
- Extended DUT logs
- FPM/ASIC-driver logs (if available)
- Route-generator traces
- Time series of latency percentiles

**Automation:**
- Script: tests/convergence/test_prefix_install_medium_churn.py
- Timeout: 60 minutes
- Tags: [medium-churn, stress]

### Test Case 6.1.3.4: High Churn Prefix Installation

**Title:** high_churn_prefix_installation

**Purpose:** Test DUT under aggressive churn to map breaking points and tail latency.

**Objective:** Measure tail latency and failure modes under heavy add/withdraw rates.

**Preconditions:**
- DUT hardware-level telemetry enabled
- Recommended to run during maintenance window as test is disruptive

**Input Parameters:**
- prefix_count: 20000
- add_rate_pps: 5000
- withdraw_rate_pps: 4000
- churn_pattern: continuous_high
- measurement_window_s: 600
- sla_ms_per_prefix: 500

**Test Steps:**
1. Configure route generator for continuous high-rate add/withdraw for measurement_window_s
2. Ensure monitoring/alerting active; capture DUT resource metrics at 1s resolution
3. Measure per-prefix install/remove latencies; track packet loss, forwarding correctness for a sample of prefixes
4. If DUT becomes unresponsive, capture last diagnostics and gracefully abort per safety policy

**Measurement Method:**
- Same per-prefix measurement
- Track percentiles (50/90/95/99/99.9) and maximums
- Record number of install failures and number of missed updates

**Expected Result:**
- 95th_percentile_latency_ms may exceed normal SLA but tail should be bounded (document soft-fail thresholds)
- No data-plane blackholes for prefixes that were installed successfully

**Pass Criteria:**
- Primary objective: characterize behavior and document thresholds
- Mark PASS if DUT stays up and recovers; else FAIL

**Artifacts to Collect:**
- Full telemetry
- dmesg
- Core files
- ASIC/SDK logs
- Route-generator dump
- Per-prefix CSV

**Automation:**
- Script: tests/convergence/test_prefix_install_high_churn.py
- Timeout: 120 minutes
- Tags: [high-churn, destructive, stress]

### Test Case 6.1.3.5: Long Duration Stability Under Churn

**Title:** long_duration_stability_under_churn

**Purpose:** Validate long-run stability and steady-state latency under intermittent churn.

**Objective:** Ensure no memory leaks or degradation in installation latency over long runtime (soak test).

**Preconditions:**
- Clean DUT restart within 1 hour before test start
- Monitoring (prometheus/grafana) available for long-term metrics

**Input Parameters:**
- prefix_count: 5000
- add_rate_pps: 500
- withdraw_rate_pps: 250
- churn_pattern: intermittent_every_5_minutes
- measurement_window_s: 14400 (4 hours)
- sla_ms_per_prefix: 150

**Test Steps:**
1. Start long-duration churn pattern: every 5 minutes run a 30s burst of adds/withdraws
2. Continuously collect per-prefix installation latencies, CPU/memory, FD counts, thread counts
3. At hourly intervals compute percentile summaries and compare to initial baseline
4. At end of window, stop churn and allow system to quiesce; run regression check against baseline results

**Measurement Method:**
- Time-series of percentiles over the test duration
- Check for upward trend in latency or resource usage
- Perform statistical test (e.g., Mann-Kendall) to detect monotonic increase in mean/median latency (optional)

**Expected Result:**
- No sustained increase in median or 95th-percentile latency over time (>10% drift from baseline is a failure condition)
- No memory leaks (resident set size growth limited to < 10% over 4 hours)

**Pass Criteria:**
- Percentile drift <= 10% vs first hour baseline
- No crashes, restarts, or elevated error logs

**Artifacts to Collect:**
- Continuous telemetry snapshots
- Hourly latency summaries
- Process-level memory traces
- Route-generator logs

**Automation:**
- Script: tests/convergence/test_prefix_install_soak.py
- Timeout: 300 minutes
- Tags: [soak, stability]

## Notes

- sla_ms_per_prefix values are example targets; adjust to match your product SLAs
- Measurement must use synchronized clocks (NTP/chrony) or sequence IDs to correlate timestamps
- Where possible, use platform FIB notifications (e.g., FPM, netlink, vendor SDK callbacks) for accurate t_fib_program events rather than polling
- Include control checks for DUT CPU, memory, queue saturation and vendor-specific counters (ASIC queue depth, FIB programming latency)
- For reproducibility record exact route-generator software/version and DUT firmware/software versions
